## 项目简介

网上查症状的典型失败方式是：搜到一个吓人的病名，然后越查越焦虑。这个工具反过来做——**先用决策树排除危险信号，再谈怎么处理**，结论固定分四级，不说「可能有问题」这种废话。

线上地址：[triage.app.workbuddy.host](https://triage.app.workbuddy.host/?sharecode=AIV3ZFRC47)，不装 App、不注册也能用；登录后对话可云端保存，AI 额度从每天 5 次提到 20 次。

原生 HTML/CSS/JS，无框架、无构建，核心代码约 4 600 行（11 个 JS 模块 + 40 个数据文件）；账号、对话存储与模型调用走 WorkBuddy Cloud。

## 功能

| 模块 | 说明 |
|---|---|
| **运动损伤** | 5 棵决策树：踝关节扭伤 / 膝盖疼 / 肩部疼痛 / 腰痛闪腰 / 肌肉拉伤 |
| **常见病症** | 12 棵决策树：感冒发烧 / 咽喉痛 / 咳嗽 / 鼻塞鼻炎 / 肠胃不适 / 胃痛反酸 / 腹泻 / 头痛 / 牙痛 / 皮肤过敏 / 尿痛尿频等 |
| **AI 查病** | 流式对话、支持发图；信息不足先追问；回复按【可能是什么】【现在能做什么】【什么情况要去医院】分块着色 |
| **疾病百科** | 23 个科室、179 条疾病，按「特征 / 来源 / 解决方案」组织 |
| **结果分享** | 竖版长图（纯 canvas 绘制），微信里可长按保存 |
| **账号体系** | 手机号/邮箱 + 密码或验证码；对话云端保存；可改密码 |
| **额度限制** | 游客 5 次/天，登录 20 次/天，按天自动重置 |

四级结论长这样：

| 等级 | 含义 | 颜色 |
|---|---|---|
| L0 | 居家观察 | 绿 |
| L1 | 居家处理 | 黄 |
| L2 | 尽快就诊 | 橙 |
| L3 | 立即就医 | 红 |

## 设计要点

**每棵树的第一问，永远是最危险的那个分叉。** 决策树常见的写法是按发生率排序问题（先问「疼了多久」），但那样会把危险情况埋在第三四层。这里的顺序是先排急症：能不能负重、有没有畸形、有没有发热、有没有放射痛——危险信号一票否决直接给 L3，剩下的才进入常规分支。宁可在小概率上多问一句，也不让急症被跳过。

**结论必须是一个等级，不能是一段话。** L0~L3 四级各自绑定颜色（绿/黄/橙/红），配一句「现在做什么」和一句「什么情况必须去医院」。分级而不是描述，是因为用户真正想知道的就是「今天要不要去」；给出等级，判断就被收敛了。

**AI 的提示词里只放规则，不放事实。** 固定 system 提示词只管格式、分块、不做诊断、危险信号这四件事；患者画像每次请求注入，药物资料按需注入（检索命中才拼），再带最近 8 条对话。这样提示词不会因为塞满知识而失控，事实更新也不用改提示词。

**结构化输出协议 + 关键词配色。** 模型被要求正文前先给一句结论，再用【】分块，每块 2–4 条。前端把【】解析成卡片，并按标题关键词自动配色——命中「就医/医院/急诊」红、「药」琥珀、「现在/能做」青、「可能/是什么」紫，兜底灰。模型换个说法也能正确着色，不依赖精确匹配整句。

**信息不足先追问，不硬下结论。** 缺部位、时长、伴随症状时，模型只输出一个【需要确认】块，前端把它变成底部弹层：一次最多 3 个问题、最多两轮，每题可选可手写。用户答完不新增气泡，答案并入原确认卡，AI 接着在同一条对话里给判定。

**用药史前置，且只查非处方药。** 症状属于可自行用药的类型时，给结论前必须问一句「这次已经吃过药了吗」，选项由药物库检索出的品牌名填充。拿到后强制三件事：第一句点明「已经吃过 X，别再叠加 Y」；单独给一个琥珀色用药提醒块（间隔、不能叠加的成分、超量伤什么器官）；绝不输出剂量。药物库检索函数只查 `otc = true` 的条目，处方药不出现在选项里，剂量字段存在库中但不对外返回。

**额度按「用户发消息」计次，不按模型调用。** 一次「提问 → 弹窗 → 选择 → 回答」在底层调了两次模型，但只算 1 次：追问后的继续生成走 silent 分支，不扣次数也不触发退款。

**游客额度用设备指纹 + 本地 ID 双键，不按 IP。** 平台的边缘节点会覆盖真实 IP（实测同一台机器多次请求落在不同出口地址），按 IP 计数会把不相干的人算成一个人。所以改用「UA/平台/语言/CPU/内存/触屏点数/色彩深度/时区/canvas 渲染结果/WebGL renderer」拼成指纹做 FNV-1a 哈希，同时本地存一个随机设备 ID；两个键任一还在，计数就不会被清零——清缓存丢本地 ID 由指纹兜住，换浏览器改指纹由本地 ID 兜住。

**业务表不给前端直接读写权限。** 三张表全部开启 RLS，除对话表外，业务表不给 anon/authenticated 任何 GRANT，读写只能走 `SECURITY DEFINER` 函数（额度检查/扣减/退回、药物检索）。额度表用复合主键 `(scope, subject, day)`，跨天自然归零，不需要定时任务。

**分享长图纯 canvas 画。** 不截 DOM、不引第三方库，按固定版式绘制竖版长图，微信里长按即可保存——避免 html2canvas 这类方案在移动端字体与阴影上的偏差。

## 技术栈

| 层 | 技术 |
|---|---|
| 前端 | 原生 HTML/CSS/JS，单页多屏（`section.screen`），无框架无构建 |
| 数据 | WorkBuddy Cloud：Postgres（药物库 / 额度 / 对话）+ Auth（手机号、邮箱） |
| 模型 | 云端 LLM 流式调用，四层提示词（规则 + 画像 + 药物 + 近 8 条对话） |
| 安全 | 全表 RLS + `SECURITY DEFINER` 函数，业务表零 GRANT |
| 额度 | 设备指纹（FNV-1a）+ 本地 ID 双键，复合主键跨天归零 |
| 分享 | 纯 canvas 绘制竖版长图 |
| 数据规模 | 17 棵决策树、23 个科室 / 179 条疾病、46 条药物 |
